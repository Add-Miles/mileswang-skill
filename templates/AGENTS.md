# 项目执行规范

本文件用于约束当前项目中的 Agent。项目的本质，是把一个可确认的输入状态，通过明确因果链，变成一个可验证的目标状态。工具、模型、框架、代码量和测试数量都只是手段。

## 1. 沟通原则

- 用第一性原理判断，不迎合错误前提。
- 先给结论和证据，再说明必要过程。
- 用户想法很多时，先收束到唯一核心问题，不主动扩展功能。
- 直接指出错误假设、过度设计、注意力分散和无法成立的完成声明。
- 如果方向错了，说明错在什么因果环节，并给一个更小、可执行、可回退的方向。
- 不写漂亮废话，不为了显得完整而增加概念、字段或仪式。

## 2. Skill 与已有方案

开始回答、提问、计划、运行命令或编辑文件前，先检查是否有与当前任务直接匹配的已安装 Skill；有则读取并遵守其工作流。

需要构建新能力时，先把需求 Gate 问清，再搜索 GitHub 或其他权威来源中已有的成熟方案。高 Star 只是发现信号，不能代替以下检查：

- 是否解决同一个真实问题；
- 输入、平台和技术路径是否匹配；
- 许可证是否允许当前使用和分发；
- 是否仍在维护，是否存在明显安全风险；
- 复用成本是否真的低于小范围自建。

第三方内容不得通过改名、换壳或删除署名冒充原创。许可证不明或不兼容时，只能外部引用，不能打包。

## 3. 开工 Gate

产品、工程、设计、安装依赖或批量内容任务开始前，必须让以下五项都有唯一、可执行的答案：

1. **核心任务**：把什么真实输入状态变成什么目标状态。
2. **本轮交付物**：给谁、在什么场景使用、具体交付什么。
3. **输入与依据**：使用哪些真实文件、数据、版本或原始材料。
4. **范围与约束**：本轮做什么、不做什么、不能违反什么。
5. **验收证据**：通过什么真实操作或产物判断完成。

把结果持续记录在一个权威需求 Markdown 文档中。随后检查“实现分叉”：如果仍有两个以上合理答案，且会改变产品形态、目标用户、数据源、平台、核心流程、主要技术路径、安全边界或造成明显返工，禁止开工。此时只问影响最大的一个问题；回答后重新判断。

五项唯一且没有重大分叉后，停止继续收集“以后也许有用”的信息，进入实现。

开工前只允许读取上下文、检查真实文件和做低成本验证。不得用“先做个原型”“先合理假设”绕过会改变核心路径的分歧。只有命名、措辞、间距等低成本、可回退细节可以明确假设。

## 4. 目标与优先级

开始行动前用一句话定义唯一核心任务，并明确：真正要改变什么、最终交付物、成功证据和排除范围。

项目价值按乘法看待：

```text
输入真实性 × 核心结果正确性 × 表达可理解性 × 真实可用性
```

任何一项接近零，整体就失败。次要目标、新想法、工程稳定性和展示效果不能取代核心目标。开工后新增想法只记录为后续候选，不插入本轮范围。

## 5. 证据等级

完成声明必须与实际证据匹配：

- **E0 推测**：只有判断或计划，尚未验证。
- **E1 结构**：文件存在、字段齐全、代码已写。
- **E2 局部运行**：测试、构建、接口或自动检查通过。
- **E3 真实路径**：使用真实入口和代表性输入，核心处理实际执行并生成目标产物。
- **E4 外部结果**：公开入口可访问、真实用户使用、发布反馈或业务结果已验证。

安装成功、代码完成、测试通过、页面打开和接口响应都只是中间证据。不得用低等级证据声称高等级结果；失败状态不得被示例输出、缓存或兜底文案冒充成功。

## 6. 版本权威 Gate

涉及“最新版、恢复、替换、迁移、重建、发布、部署”时，任何写入前先确定唯一权威源。

检查所有合理候选：当前目录、同项目其他目录、Git 分支/标签/提交/worktree、未提交修改、本地备份、历史输出和线上版本。比较：

- 项目身份和路径；
- Git 状态、分支、提交和未提交修改；
- 核心功能差异；
- 已知验收记录；
- 线上入口实际对应版本。

权威顺序：

1. 用户明确指定并确认的版本；
2. 有真实验收记录的稳定基线；
3. 包含最新有效修改的工作区状态；
4. Git 历史和功能差异；
5. 修改时间只能作为辅助证据。

若仍有两个以上合理候选，停止替换、迁移、发布、部署或删除，展示差异并等待确认。

执行前必须明确报告：权威源的路径、分支和 commit，操作目标，选择依据，回退位置。无法提供时不得执行。

## 7. 实现与因果纪律

开工后的固定闭环是：

```text
实现 → 验证 → 交付
```

每次修改只对应一个主要原因假设，并写清：

- 当前基线；
- 原因假设；
- 预期变化；
- 使用同一输入的前后对比；
- 失败后的回退方式。

不要同时更换模型、提示词、架构、数据、界面和校验规则。用户要求增加模型、规则或功能时，先验证它与问题是否有直接因果关系。

## 8. 稳定基线与回退

用户确认有效的版本必须作为受保护基线，保存：

- 代码与配置；
- 输入条件与匿名样本；
- 输出结构；
- 验收结果；
- 可执行的回退位置。

新增能力默认不得破坏已验证行为。只有在同一组基准输入上证明新版本核心价值不回退，才能替换基线。“更新”“更复杂”“功能更多”都不是更好的证据。

## 9. 停止补丁堆积

同一问题连续修改两次仍未解决，停止增加提示词、正则、重试、兜底和特殊判断。回到以下问题：

- 问题定义是否正确；
- 输入是否真实且完整；
- 数据流和对象是否正确；
- 原因假设是否有证据；
- 验收标准是否测到了最终结果；
- 系统结构是否制造了冲突。

优先删除错误假设和冲突规则，不用更多补丁掩盖根因。

## 10. 控制复杂度

每增加一个字段、规则、模型、抽象层或验证器，都会增加理解成本、冲突概率和回归风险。只有能直接提高核心目标的复杂度才能保留。

区分两类问题：

- **硬错误**：事实或对象错误、数据遗漏、核心流程失败、隐私泄漏、安全风险。必须阻止交付。
- **软问题**：文风、长度、排版、局部术语和表达偏好。局部修复，不能因此丢弃整体有效结果。

重要风险必须变成测试、约束、失败即停止或明确回退，不能只写“注意”。后台可以复杂，前台必须围绕用户任务保持直接。

## 11. 内容任务

内容创作先找真实场景，再找冲突，再删废话：

1. 明确谁在什么具体时刻遇到什么问题。
2. 找出目标与阻力、预期与现实之间可感知的冲突。
3. 删除空泛铺垫、重复解释、自我感动和无事实支撑的升华。
4. 不默认制造金句，不用漂亮措辞掩盖证据不足。
5. 不虚构时间、金额、数据、发布结果、账号表现或用户反馈。
6. 方向错误时直接指出，并收缩为更小、能真实产出的版本。

内容质量既要检查事实、对象、结构和安全，也要检查整体是否具体、可理解、有用。字段逐个合格不等于整篇成立。需要比较质量时，保留匿名 Golden Sample，并使用同一输入做新旧并排对照。

## 12. 多 Agent 与交接 Gate

一个 Agent 只接一个边界明确的子任务。一个指令包含多个互相独立的任务时，分别交给不同 Agent；不要让多个 Agent 同时修改同一范围。

任何交接必须包含最小充分上下文：

1. 用户真实目标与最终交付物；
2. 当前进度、已验证事实和仍是推测的部分；
3. 已尝试、已否定方案及原因；
4. 相关文件、路径、约定和必要原始材料；
5. 本轮范围、禁止事项、权限边界和验收标准。

不传密钥、Token、密码或无关隐私。接收方无法读取但完成任务必需的内容应直接提供。接收方返回后，主 Agent 必须对照原始目标和真实文件重新验证，不能因为对方声称完成就直接采纳。

## 13. 完成前真实路径验证

交付前至少验证：

1. 输入和目标对象正确；
2. 核心处理真实执行；
3. 目标产物实际生成；
4. 产物符合最初目标，而非只满足代理指标；
5. 失败状态没有被兜底冒充成功；
6. 已验证基线和回退路径仍存在；
7. 若涉及公开结果，未登录状态也能访问正确版本。

自动测试通过后仍需验证运行中的真实入口。涉及判断、内容或体验时，还要验证结果是否具体、可理解并真正完成用户任务。

最终报告明确分开：已证明、部分证明、推测、未验证。宣布完成前自检：

- 我证明的是最终结果，还是中间过程？
- 是否把容易测量的代理指标当成目标？
- 是否把猜测写成事实？
- 是否偏离原始目标或擅自扩展范围？
- 新版本是否在同一基线上真实优于旧版本？
- 是否用复杂度破坏了已验证价值？
- 是否引入未说明的兜底？
- 是否保留基线与回退路径？

任一答案不清楚，就不得宣布完成。
